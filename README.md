# asmai

AsmAI (short for AssemblyAI) is a personal software engineering **factory**: a coordinated group of AI agents that does software engineering work for one user across the repositories they register with it.

The project is at an early stage (milestone M1, the walking skeleton, is under way). This repository is the Go module `github.com/talvor/asmai`; so far `asmai` runs the per-user daemon and its store, with Coordination's leader in a terminal the daemon owns (see [Running the factory](#running-the-factory)), installs its pinned Claude Code (see [Pinned providers](#pinned-providers)), and prints its version (`asmai version`) and its license with the third-party notices (`asmai notices`).

## Two repositories

AsmAI was planned in [talvor/AssemblyAI](https://github.com/talvor/AssemblyAI) and is built here.

- **talvor/AssemblyAI keeps the planning record**: the map, the decision tickets, the Lavish records and the specification (`docs/spec/`). It is not where AsmAI is built.
- **talvor/asmai holds AsmAI's code**, its implementation tickets and its releases.

Only [`GLOSSARY.md`](GLOSSARY.md) and ADRs 0001 to 0010 were copied across from talvor/AssemblyAI. They now evolve here, and new ADRs are numbered from 0011.

## What it does

You talk to the **Coordination** role in an interactive terminal and ask for an outcome: a **job**. Each job has a mandate and acceptance criteria, and targets at most one registered repository. The factory splits the work between roles: Coordination, Planning, Research, Engineering and Quality. Each role has one **leader**, and the leader hands bounded **assignments** to **workers**. Decisions that need your authority come back to you as **escalations**. Everything else is decided within the mandate and recorded as a delegated decision.

A repository job ends in a **tested pull request**. Quality has validated its exact head commit, the repository's CI has passed on it, its base has been taken in, and the PR states its evidence and gaps. The factory never merges. Merging stays your decision.

## How it is built

- **One Go executable** (`asmai`) is the daemon, the human CLI and the agent CLI, with SQLite built in. It installs without root ([ADR 0003](docs/adr/0003-go-executable-runs-pinned-providers.md)).
- **A per-user daemon owns the agent terminals.** Agents run inside unmodified Claude Code and Codex CLIs. They outlive your terminal and SSH session, and you attach with `asmai attach`. The attach client draws a status line showing what is waiting on you ([ADR 0001](docs/adr/0001-daemon-owns-agent-terminals.md), [ADR 0004](docs/adr/0004-attach-client-draws-status-line.md)).
- **Agents coordinate through the `asmai` CLI.** The daemon is the only writer to the store: the current state plus an append-only journal ([ADR 0002](docs/adr/0002-agents-coordinate-through-asmai-cli.md)).
- **Pinned providers and skills.** Agents never use your personal Claude Code, Codex or skills. AsmAI installs pinned, qualified copies and passes hooks, instructions and its pinned skill bundle to each session. Lavish ships as a Deno-compiled executable, so the host needs no Node ([ADR 0003](docs/adr/0003-go-executable-runs-pinned-providers.md), [ADR 0006](docs/adr/0006-agents-use-only-the-pinned-skill-bundle.md), [ADR 0010](docs/adr/0010-lavish-is-a-deno-compiled-executable-built-per-pin.md)).
- **Jobs work in an AsmAI-owned clone.** Your checkout is never touched. The job branch moves only when a result is accepted ([ADR 0005](docs/adr/0005-jobs-work-in-an-asmai-owned-clone.md), [ADR 0007](docs/adr/0007-asmai-delivers-tested-prs-with-its-own-roles.md)).
- **Releases are qualified, not just tested.** Qualification runs the real pinned provider CLIs on real hosts with deliberately injected faults. A release is the qualified commit plus its qualification record ([ADR 0008](docs/adr/0008-qualification-runs-real-provider-clis-on-real-hosts.md), [ADR 0009](docs/adr/0009-a-release-is-the-qualified-commit-plus-its-record.md)). The hosts qualification runs on are listed in [`docs/qualification-hosts.md`](docs/qualification-hosts.md).

## Fixture repository

[talvor/asmai-fixture](https://github.com/talvor/asmai-fixture) is a small, separate repository used as a target for delivery cases from M1 onwards. It holds a hello-world Node.js module, a test, and one pull request check, `CI / test`, whose outcome each PR can switch through a `.ci-mode` file on its branch:

| Mode   | Result on the PR                                                    |
|--------|---------------------------------------------------------------------|
| green  | Default. Tests run and the check passes                             |
| red    | Tests run, then the check fails                                     |
| slow   | The check stays in progress for a chosen number of minutes (past 15 works), then passes |
| absent | No check runs at all                                                |

Switch with `scripts/ci-mode.sh <mode> [minutes]`, then commit and push. See the [fixture README](https://github.com/talvor/asmai-fixture#readme) for details.

## Running the factory

The first run is `asmai init`, then `asmai start`. `asmai init` does what the factory needs once, in five stages, each under a numbered heading such as `== 2/5 Config`. `asmai setup`, its name in the first milestone, still runs it. With `--yes`, it uses `opus` for Claude's default model unless `--claude-default-model` supplies another model, installs the pinned Claude Code and opens Claude Code in each folder without asking either question; Claude Code's own question about trusting a folder is still yours to answer. Each stage first says what it is about to do, then skips each step already done, printing one line for each, `done` or `already done`; a step that fails prints `failed`, followed by the error, which says what to do next:

1. **Platform.** It checks that this platform is certified (Linux on x86_64 or macOS on Apple silicon); anywhere else it fails, naming what to do, and nothing more runs.
2. **Config.** If `~/.config/asmai/config.toml` is missing, it asks in a terminal for Claude's default model (suggesting `opus`) and writes it with Coordination, Engineering and Quality staffed and no repositories. `--claude-default-model MODEL` supplies any nonempty model name without a prompt, including with `--yes` (see [The configuration file](#the-configuration-file)). An existing file is never changed: init reports its problems, including conflicts with registered repositories, as `asmai start` does.
3. **Folders.** It makes the folders of the state directory, `~/.local/state/asmai`, including `agents/`, which holds the leaders' directories, and `workspaces/`, which holds each assignment's workspace.
4. **Claude Code.** It installs the pinned Claude Code, as `asmai providers install` does, once you confirm (see [Pinned providers](#pinned-providers)), then checks that it reports exactly the pinned version, that its own `auth status --json` reports a `claude.ai` subscription sign-in, and that this account lets AsmAI's own permission rules take effect (see [Under a Claude Code managed policy](#under-a-claude-code-managed-policy)). A failed provider check stops init before it opens Claude Code for trust and names the fix. AsmAI never starts a sign-in.
5. **Trust.** Claude Code asks whether to trust a folder the first time a session starts there, and only Coordination's terminal takes your keys, so every other agent would wait at that question. Trusting a folder also trusts every plain folder below it, so setup opens the pinned Claude Code in `agents/`, then in `workspaces/`, in your terminal. A git repository is another matter: Claude Code trusts it, and every worktree of it, only through the repository's own trust, and each worker starts in a git worktree of AsmAI's clone of a registered repository. So setup also opens Claude Code in each registered repository's clone, `repositories/<name>`, and `asmai repo add` runs this same step for the clone it makes. Before each, it prints a framed block naming the folder and why agents need it, the question Claude Code will ask, the answer to choose, "Yes, I trust this folder", and what "No, exit" does, then waits: press Enter to open Claude Code, or type `n` and Enter to stop setup, which then exits 1 naming the folder still untrusted, having opened nothing. In Claude Code, choose "Yes, I trust this folder", then leave it with `/exit`. Claude Code records your answer itself; AsmAI never writes `~/.claude.json` or `~/.claude`. If you choose "No, exit", setup names the folder still untrusted and exits 1, and running it again asks only about that folder. Trusting needs you at a terminal: with a folder untrusted and standard input not a terminal, setup opens no Claude Code and exits 1, saying so. The `repositories/` folder itself and `views/` are not trusted, because no agent starts there.

Run again, every step is `already done`, and init asks nothing and opens no Claude Code. You can repeat `--claude-default-model` with the same value after a partial run. An existing configuration is unchanged; a different flagged value is reported, and you must edit `[providers.claude].default_model` in the file to change it. See [ADR 0011](docs/adr/0011-agents-rely-on-one-user-given-directory-trust.md).

`asmai start` starts the per-user daemon in the background and returns once it answers; `asmai start --foreground` keeps it attached to the terminal, showing its log, until `asmai stop` or Ctrl-C. Each user runs at most one daemon: a second start reports the running factory. Commands that manage the running factory reach it over a Unix socket in the state directory; file-based configuration commands also work while it is stopped. The daemon opens no network listener.

`asmai doctor` runs the same checks as init and start, without changing anything or asking anything, and prints them under the platform, the provider pin, the configuration file and the state directory, exiting 1 if one fails, with its fix. It then reports what the other commands do not: what skill hiding cannot cover (the pinned Claude Code's built-in slash commands, which stay typable in an agent's terminal though it refuses an agent's calls to them), each added skill and each switched-on repository skill, marked unqualified because no release qualifies them, and whether upstream has a newer skill release than the bundle's. The release lookup asks GitHub for upstream's latest release and reads nothing else; when it cannot be reached, doctor says so and still passes.

Every start then runs the checks that exist: this platform is certified (Linux on x86_64 or macOS on Apple silicon: anywhere else no agent starts, and the check says so), the roles are staffed in the configuration file, the pinned Claude Code is installed and reports exactly the pinned version, its own status reports a `claude.ai` subscription sign-in, Claude Code applies AsmAI's own permission rules on this account ([see below](#under-a-claude-code-managed-policy)), and Claude Code trusts `agents/`, `workspaces/` and each registered repository's clone, which the daemon reads from Claude Code's own record in `~/.claude.json` without changing it. If they pass, the daemon starts Coordination's leader, which runs for as long as the factory runs. If one fails, `asmai start` names it and the fix and exits 1, and the daemon keeps running without starting the leader (a leader already running keeps running), so that you can fix it, for example with `asmai init`, and run `asmai start` again. `asmai start` itself never asks anything. Before it starts any agent, the daemon reads the record again, and refuses to start one whose folder Claude Code does not trust, naming `asmai init`, rather than leave it waiting at the question: for a worker, that is the clone its workspace is checked out from.

### The configuration file

The configuration file is `~/.config/asmai/config.toml`, on Linux and macOS alike, and only you change it: agents never do. `asmai init` writes it when it is missing, staffed as below, and never changes it after. It has one table for each of `[limits]`, `[logs]`, `[providers.claude]`, `[roles.<role>]` and `[repositories.<name>]`; every field not written has a default. Claude is the only provider so far: `[providers.codex]` and `"codex"` as a role's provider are refused, with a message that Codex arrives in a later asmai. Durations are written like `"30s"`, `"10m"` or `"14d"`, and sizes like `"5GB"` (decimal units).

The staffing of a role, which `asmai init` writes:

```toml
[roles.coordination]
leader_provider = "claude"
leader_model = "opus"
worker_provider = "claude"
worker_model = "opus"

[roles.engineering]
leader_provider = "claude"
leader_model = "opus"
worker_provider = "claude"
worker_model = "opus"

[roles.quality]
leader_provider = "claude"
leader_model = "opus"
worker_provider = "claude"
worker_model = "opus"
```

| Table | Fields |
| --- | --- |
| `[limits]` | `leader_idle_grace`, `leader_restarts`, `leader_restart_window`, `silence_timeout`, `drain_timeout`, `side_effect_free_retries`, `provider_error_resumes`, `provider_error_wait`, `provider_error_wait_max`, `recheck_interval`, `dispatch_limit`, `failed_validations`, `first_check_wait`, `free_space_floor` |
| `[logs]` | `daemon_files`, `daemon_file_size`, `recording_retention` |
| `[providers.claude]` | `worker_cap`, `default_model` |
| `[roles.<role>]` | `leader_provider`, `leader_model`, `worker_provider`, `worker_model`, `leader_skills`, `worker_skills`, `leader_added_skills`, `worker_added_skills` |
| `[repositories.<name>]` | `location`, `origin`, `default_branch`, `notes`, `checks_one_at_a_time`, `no_ci`, `commit_trailers`, `repository_skills` |
| `[[repositories.<name>.writable]]` | one table for each [writable folder](#writable-folders): `path`, `env` |

Three repository settings take effect in this asmai already. `notes` is your notes for the repository: they reach the repository's workers after its instruction files (`AGENTS.md`, `CLAUDE.md`), as instructions. `commit_trailers = false` switches off the `AsmAI-Job`, `AsmAI-Agent` and `AsmAI-Dispatch` trailers on that repository's commits, for a repository whose conventions forbid them; it is read at each commit. The `[[repositories.<name>.writable]]` tables name folders outside a workspace that the repository's workers may write, as [Writable folders](#writable-folders) describes.

`asmai config check` reads the file and reports every problem in it, each with its line and the fix, and exits 1 if there is any. `asmai config example` prints an example with every default written out, for one role and one repository, which passes `asmai config check`. `asmai start` refuses a file it cannot honour in the same way, naming the line and the fix: TOML that does not parse, a table or field it does not read, a value of the wrong type or out of range, a provider other than `"claude"`, or a role or field left out.

### Changing the configuration

You can edit the file by hand or with `asmai config edit` and `asmai role set`. `role set` preserves the rest of the file, including comments; `config edit` saves the copy you edited after validation.

- `asmai config show` prints the effective configuration: every setting, with the defaults of the ones the file does not set, such as each role's default skill lists. With `--json` it prints the same as nested objects.
- `asmai config edit` opens a copy of the existing file in `$VISUAL` or `$EDITOR`; run `asmai init` first if the file is missing. What you save replaces the file only when it has no problem, as `asmai config check` counts them, including a role the factory runs that is not staffed. A file with problems is shown them with their lines and fixes, and you edit it again, or the file stays as it was. If the file changes while you edit, your edited copy remains at the path printed in the error.
- `asmai config apply` hands the file to the running daemon, which validates it and shows what differs from the configuration the factory last started on or applied. For each change it names the affected agents; provider and model changes reach them at their next start, while `commit_trailers` affects a running worker's next commit. A change to a repository's writable entries shows which declarations are added or removed, including both sides of a changed entry, and every apply names each folder each repository opens outside its workspaces, changed or not. For a change that adds or removes skills, it shows which skills, and the agents, running or stopped, that pick them up at their next start; running agents keep the skills they started with. Other changes that affect no running agent apply at once. Once you confirm, the daemon journals the applied configuration as `configuration.applied`, with the file, its SHA-256 and each change with its agents. Repository presence, location, origin and default branch belong to registered records and change only through `asmai repo add` and `asmai repo remove`; a conflicting file entry is reported by `asmai status` and `asmai config check` and refused by apply. If the daemon started without staffed roles, apply the completed file before starting agents. Restarting the daemon reads the file on disk as its confirmed configuration. With the factory stopped there is nothing to apply: it reads the file when it starts.
- `asmai role list` shows each role's staffing and skill lists, and `asmai role set <role>` sets the provider and model of its leader and workers with the four explicit `--leader-…` and `--worker-…` flags. It refuses `codex`, which arrives in a later asmai. Running agents keep what they run on until their next start, and `asmai config apply` shows which they are.

### Repositories

Jobs can target only repositories you have registered, and only you register them. `asmai repo add <path-or-url>` takes a local checkout (from anywhere inside it), a URL, or a bare repository on this host standing in for one. It records the repository's name, its location on the host, its origin remote and its default branch, in the store and as `location`, `origin` and `default_branch` in the repository's `[repositories.<name>]` table, which it appends to the configuration file without touching anything else in it:

```toml
[repositories.otman]
location = "/home/me/src/otman"
origin = "git@github.com:me/otman.git"
default_branch = "main"
```

The name is the last part of the origin without `.git`, or what `--name` says. The origin is the checkout's `origin` remote, or the URL itself; a checkout with no `origin` is refused, and so is a URL that carries a password, because AsmAI handles no tokens: git's own credential helpers and SSH keys do. The default branch is the one the origin names. `location` is empty for a repository registered by its URL.

`asmai repo add` accepts every other field of the entry too, written only when it differs from its default: `--default-branch` (a branch origin has, for jobs to start from, not the one its HEAD names), `--notes`, `--checks-one-at-a-time`, `--no-ci`, `--commit-trailers=false`, `--repository-skills <role>` (repeated for each role) and `--writable <path>[=<ENV>]` (repeated for each folder, see [Writable folders](#writable-folders)). It refuses an unknown role or a folder named with `--writable` that the bounds below close before cloning. It checks the named branch in the new clone, removing that clone if the branch is absent.

`asmai repo add` also makes AsmAI's own clone of the repository in `repositories/<name>` in the state directory, cloned from the origin with your git and its configuration, never prompting for a password. Jobs work in that clone; your own checkout is recorded and never used, so it stays as it is. A registration that fails leaves no clone, entry or record. Each worker starts in a git worktree of the clone, which Claude Code trusts only once you trust the clone itself, so `asmai repo add` then has you trust the clone as setup's [trust step](#running-the-factory) does: the same framed block naming the clone and why, the same wait for Enter (or `n` to stop), and the same answer in Claude Code. If you stop, or choose "No, exit", it exits 1 naming the clone still untrusted, with the repository registered, and `asmai init` takes it up again. A clone already trusted is reported already done, and no Claude Code is opened. With standard input not a terminal, or before `asmai init` has installed the pinned Claude Code, `asmai repo add` registers the repository, opens nothing, says the clone still needs trusting and to run `asmai init` in a terminal, and exits 0. With `--json`, standard output holds only the result, and the trust step draws on standard error. Until the clone is trusted, `asmai start` fails its directory trust check naming the clone, and the daemon starts no worker in a workspace of it.

`asmai repo remove <name>` removes the record, the entry in the configuration file (with the comment lines right above it) and the clone, and is refused while the repository has an open job. Your checkout is not touched. An entry you wrote by hand in another form than a `[repositories.<name>]` table is yours to remove. The journal records each `repository.added` and `repository.removed`.

### Writable folders

Without a declared writable folder, a worker's commands cannot write a language's build cache outside its workspace and temporary directory: `go test`, `go vet` and `go build` cannot use `~/.cache/go-build`. A repository's entry declares the folders its workers may write besides, one `[[repositories.<name>.writable]]` table each, with a `path` (a literal path, `~` allowed) and an optional `env`, the name of an environment variable the worker's session carries the folder's absolute path in:

```toml
[repositories.otman]
location = "/home/me/src/otman"
origin = "git@github.com:me/otman.git"
default_branch = "main"

[[repositories.otman.writable]]
path = "~/.cache/go-build"
env = "GOCACHE"
```

When a worker of a job on that repository starts, Engineering's and Quality's alike, the daemon resolves each folder to an absolute path, makes it if it is missing, adds it to the worker's write guard, and sets each `env` to that path in the worker's environment, over any value the daemon inherited, so that the worker's tools use the folder the guard opened even when your shell sets another. A leader's session, and a worker of another repository's job, get neither. The daemon uses only what the file says: nothing is computed from the language at start.

`asmai repo add` detects the language once from marker files in the selected default branch's checked-out tree and writes the suggested folders into the entry, only when there are some. A `go.mod` suggests `~/.cache/go-build` exported as `GOCACHE`; no other language ships a default, and another is one line in the detection table. `--writable <path>[=<ENV>]`, repeated for each folder, sets the entry's folders by hand and replaces the suggestion. A repository registered earlier gets the tables by hand, then `asmai config apply`; the module cache stays read-only, because checks only read it once modules are downloaded.

A folder is refused, by `asmai config check`, `asmai config apply`, `asmai repo add` and again when a worker starts, with a message naming the reason, when it is:

- the home directory or one of its ancestors;
- `~/.ssh`, `~/.claude`, `~/.claude.json`, the state directory or a clone, or a folder inside one of them (a path that reaches one of these or the home directory through a symbolic link is refused too);
- not an absolute path or one starting `~/`.

A variable name is refused when it is not an identifier, is `HOME`, `PATH` or `TMPDIR`, or starts `GIT_` or `ASMAI_`, which covers the slot variable `ASMAI_SLOT`; two folders of one repository may not export the same name. `asmai config check` and `asmai config apply` name every folder each repository opens outside its workspaces, and `asmai repo show` names the repository's.

An entry refused for more than one reason reports one reason at a time; fixing it may reveal the next.

### Agents

Coordination's leader runs the pinned Claude Code in a pseudo-terminal the daemon owns. Everything the session is given is on its command line: `--settings` with a hook for each lifecycle event (session start, prompt submission, permission request and stop), the permission rules for `asmai` and selected git and gh operations, and the [write guard](#the-write-guard-commits-and-repository-files); an empty `--setting-sources`, `--strict-mcp-config` and `--plugin-dir` with the plugin its [skills](#skills) are delivered in; its model; and Coordination's instructions, appended to its system prompt. AsmAI never writes `~/.claude`, and never skips Claude Code's permission checks or hook review: it passes no flag that skips them, and the settings disable bypassing permissions, whatever your own settings say. Each session's settings set its permission mode, which depends on whether anyone can answer a native prompt in its terminal ([ADR 0012](docs/adr/0012-agents-without-the-users-terminal-are-denied-instead-of-prompted.md)):

| Agent | Permission mode | What its rules do not allow | Files its Edit and Write tools change without a prompt |
|---|---|---|---|
| `leader@coordination` | `default` | raises Claude Code's native prompt, which you answer in the conversation | none |
| `leader@engineering`, `leader@quality` | `dontAsk` | is denied, with no prompt, and the agent is told so | none |
| every worker | `dontAsk` | is denied, with no prompt, and the agent is told so | its workspace and its temporary directory |

Only Coordination's terminal takes your keys, so a native prompt in any other agent's would wait for an answer nobody can give. In `dontAsk` mode Claude Code gives no approval its rules do not give: the agent uses an allowed route, or reports what was denied, a worker with `asmai blocked` and a leader through Coordination. Workers are told to write files with the Edit and Write tools, never with shell heredocs or `cat > file`: Claude Code denies those its shell analyser marks too complex to check, such as one with a brace next to a quote character, and may run plain ones in the sandbox. AsmAI never uses auto mode, which would have a classifier approve in your place.

The session starts with the daemon's environment, less any provider API-key variable such as `ANTHROPIC_API_KEY`, so it runs on your subscription. Each hook runs the daemon's copy of `asmai` at its fixed path, `bin/asmai` in the state directory, which reports the event to the daemon; the daemon journals it as an observation of that session's generation. A `session.started` journal entry records the provider version, the command line passed (never the environment) and the generation, and a `session.ended` entry records how the session ended.

Each agent session receives `ASMAI_SESSION` in its environment. The CLI sends it with each daemon request; without it the caller is the user. The daemon checks the credential against the running session's role, leader or worker kind, and generation. A stale or unknown credential is refused. An agent can run only its coordination commands; for a factory-changing command, AsmAI tells it what to ask the user to run. This guard and the witnessed-message attribution prevent mistakes and keep authority clear. They are not a security boundary against a process running with the user's own access.

#### Under a Claude Code managed policy

An agent can run its commands without a prompt only because AsmAI passes its own permission rules to Claude Code with `--settings`: `Bash(asmai:*)`, the `git` and `gh` rules, and the Read and Edit rules for a worker's workspace and temporary directory. They take effect only when Claude Code applies permission rules from `--settings`. An organization's managed settings can switch that off with `allowManagedPermissionRulesOnly: true`: Claude Code then applies only the permission rules of managed settings and ignores AsmAI's, so every command an agent needs raises a native prompt, which nobody answers in an unattended agent's terminal, or is denied in `dontAsk` mode. The work stops at the first command, and nothing says why.

So `asmai start` and `asmai init` ask the pinned Claude Code itself, before any agent starts: they start it in print mode with AsmAI's command rules in `--settings` and no settings source of its own, and ask for the permission rules it applies, which it answers from its own settings, managed settings included, with no model call, no prompt and no noticeable delay. If it lists any of AsmAI's rules as not in effect, the check `permission rules` fails, naming `allowManagedPermissionRulesOnly` and the rules, and no agent starts. You can:

- run AsmAI under an account without that policy; or
- have an administrator add the rules AsmAI needs to the managed settings' `permissions.allow`. The command rules are listed in the failed check and are, in `asmai`, `Bash(asmai:*)`; for git, `Bash(git add:*)`, `Bash(git commit:*)`, `Bash(git push:*)`, `Bash(git fetch:*)`, `Bash(git ls-remote:*)`, `Bash(git status:*)`, `Bash(git rev-parse:*)`, `Bash(git merge:*)` and `Bash(git var:*)`; for gh, `Bash(gh pr create:*)`, `Bash(gh pr view:*)`, `Bash(gh pr list:*)`, `Bash(gh pr checks:*)`, `Bash(gh pr status:*)`, `Bash(gh issue view:*)`, `Bash(gh run view:*)`, `Bash(gh run list:*)` and `Bash(gh run watch:*)`. A worker's Edit and Write tools need `Read` and `Edit` rules, written `Read(//<state directory>/workspaces/**)` and `Edit(//<state directory>/workspaces/**)`, for its workspace and its temporary directory, both under `workspaces/`. With the rules in the managed settings, the check passes.

AsmAI never writes or overrides managed or user Claude Code settings. See [ADR 0013](docs/adr/0013-asmai-refuses-to-start-where-claude-code-ignores-its-permission-rules.md).

Agents are addressed `name@role`, and a role alone means its leader: `asmai attach coordination` is `asmai attach leader@coordination`. `asmai attach` draws the agent's screen itself from AsmAI's own terminal emulation, with the agent's terminal one row shorter than yours and a status line on the last row. Should an agent other than Coordination's leader still raise a native prompt, which its session reports through its permission request hook, `asmai status` and every status line show it, such as "worker1@engineering waits at a native prompt nobody can answer", with what it asks to do, until the session reports another event. Attaching only observes: what you type does not reach the agent. Only the conversation carries your keys, to Coordination.

### The write guard, commits and repository files

Every agent session runs inside Claude Code's write guard, its sandbox for the commands it runs, which the session's settings switch on with `failIfUnavailable`: a session whose guard cannot start does not start. On Linux the guard needs `bubblewrap` and `socat`. Commands in the guard write only in the agent's working directory, a worker's own temporary directory and the system's, and, for a worker, the [writable folders](#writable-folders) its job's repository declares, such as a build cache; they reach a network host only once you approve it, at Coordination's prompt: every other agent is denied. The commands that need your credentials, your network and the daemon run outside it, and are allowed without a prompt: `asmai`, the Git subcommands workers need, and selected `gh pr`, `gh issue view` and `gh run` operations. Other commands, including `git config`, `git diff` and `gh config`, stay inside the guard. `echo` is left alone too, so that a compound command of `asmai` commands and `echo`, such as `asmai brief 1; echo ----; asmai inbox`, runs outside the guard and reaches the daemon without a prompt. On macOS the guard also lets a command connect to the daemon's own socket, `daemon.sock` in the state directory, and to no other Unix socket, so that an `asmai` command the guard runs in a compound command with other commands still reaches the daemon. On Linux Claude Code's guard cannot allow one socket alone, so such a command reaches no daemon there, and its retry outside the guard raises the native prompt in Coordination's terminal and is denied in any other agent's. The same holds for a worker's `git commit` and `git push`: a call that holds either stays in the guard unless every command in it is one of those left alone, so workers are told to run each as its own single, plain call, never chained, piped or after a `cd`, and the daemon's refusal of a result whose commit is not on origin says so. So every agent's instructions tell it to run each `asmai` command as its own single command in its own Bash call, never chained or compounded with others. Anything else the guard does not allow raises Claude Code's native prompt in Coordination's terminal, which waits for you, and is denied in any other agent's. The guard is a guard against mistakes, not a security boundary, and workers are told to stay inside their workspace and to record any write outside it as an effect. A writable folder widens it by that folder, and a worker could poison a cache your own builds use: the bounds on what a repository may declare refuse only the obvious mistakes ([ADR 0016](docs/adr/0016-a-repository-declares-the-folders-its-workers-may-write.md)).

Workers commit as you. Git runs with your own configuration, so commits carry your name and email, and `git push` and `gh` use your existing credentials: AsmAI sets no identity, stores no token and writes nothing to the clone's configuration. Every commit a worker makes carries three trailers (unless the repository sets `commit_trailers = false`, see [The configuration file](#the-configuration-file)), which the worker's git adds through a hooks directory AsmAI gives it, `githooks/` in the state directory, whose hooks run `asmai git-hook`:

```
AsmAI-Job: 1
AsmAI-Agent: worker1@engineering
AsmAI-Dispatch: 3
```

The job and dispatch are the daemon's, for the assignment the worker is on. A commit that cannot carry them is refused. AsmAI adds the trailers after the repository's `prepare-commit-msg` hook, including when the worker uses `git commit --no-verify`, and again after its `commit-msg` hook, so that a merge commit carries them too even when that hook rewrites the message. It forwards the repository's other hooks according to Git's normal hook rules. After a commit, it checks the final message and amends it if a repository hook changed a trailer. The repository's hooks run in the system's sandbox, Seatbelt on macOS and Landlock on Linux, as `git commit` itself runs outside the write guard: a hook writes only in the workspace, the workspace's own Git directory, which holds the message being committed and the index, the objects, refs, reflogs and `packed-refs` of the clone's shared Git directory, so that its own `git add` and `git stash` work, the system's temporary directory and the worker's. Any other write fails, including to the rest of the clone's shared Git directory, its `hooks`, `config` and `info`, so a hook cannot change the hooks or configuration Git runs with, and the commit goes on as the hook decides. Landlock cannot let a hook create `packed-refs.lock` without letting it create files across the shared Git directory, so on Linux a hook cannot delete a ref: dropping the last stash entry, as lint-staged does, succeeds but leaves a stale `refs/stash` behind. A hook that cannot be confined, on a Linux kernel without Landlock, does not run, and its commit is refused.

Workers follow the repository's instruction files, `AGENTS.md`, `CLAUDE.md` and `.claude/CLAUDE.md`, whichever exist, but never its Claude Code configuration. Claude Code loads instruction files only along with a repository's own settings, so AsmAI reads these three files from the workspace and appends them to the worker's instructions, and starts the session with an empty `--setting-sources` and `--strict-mcp-config`: the repository's `.claude` settings, hooks, permission rules and MCP servers never load. The instruction files decide how work is done in the repository, never what the worker is asked to do, and never how the branch is pushed. [Qualification](docs/qualification-harness.md) cases C36 and C37 check both on the pinned Claude Code, and C49 that a worker writes files with the Write tool without a prompt and is denied, not prompted, a shell write Claude Code cannot check.

### Skills

Every Claude Code agent AsmAI starts is given its role's skill list: `leader_skills` or `worker_skills` in its `[roles.<role>]`, or the role's default list, from the embedded skill bundle, with the role's added skills. For a nonempty list, the daemon writes its skills into a per-session plugin named `asmai` at `plugins/<agent>/` in the state directory and starts the session with `--plugin-dir` naming it. Planning, Research and Quality leaders have empty default lists, so they receive no plugin unless the configuration gives them skills. Every session still starts with an empty `--setting-sources`, so the user's own skills, which live in the user setting source, and a repository's skills in `.claude/skills` never reach it, except repository skills switched on as below. Its settings also hide Claude Code's own skills, its built-in `code-review` among them, with `disableBundledSkills` and, for the few it lists besides, `skillOverrides`. What the pinned Claude Code cannot hide is recorded for `asmai doctor` to list: its built-in slash commands, such as `/security-review` and `/init`, stay typable in an agent's terminal, though Claude Code hides them from the agent and refuses its calls to them. [Qualification](docs/qualification-harness.md) case C33 checks that a session lists only its own skills. A session with a plugin may read its files without a prompt. A leader has its role's leader skills (Coordination's `ask-matt` and `wait-what`, Engineering's `pr`), and a worker has its role's worker list.

An assignment names the skill its worker is to run and may narrow its list: `asmai assign --skill <name> --narrow <skill> ...`. A list is only narrowed, never widened, and the skill named stays on it. The worker is started with the narrowed list, and says which skills it ran with `asmai result --skill <name>`, which must be on that list. Claude Code names a plugin's skills with the plugin's name ahead of their own, such as `asmai:tdd`, while upstream's skills call each other by bare name, such as `/tdd`: the operating guide in every agent's instructions says that the skill of that name on its list is the one to run. [Qualification](docs/qualification-harness.md) case C34 checks on the pinned Claude Code that a skill naming another by bare name leads to a successful Skill tool call.

The bundled copies of upstream's manual-only skills allow AsmAI agents to invoke them by name. Their upstream request-only status remains in the bundle manifest for the operating guide and leader indexes. The dispatch fingerprint covers the delivered text. See [The skill bundle](CONTRIBUTING.md#the-skill-bundle) for how its patches are maintained across a sync.

Known limitation: an in-flight assignment uses the role's current list when a later session starts. If a release changes those defaults or removes a bundled skill, its previously named skill or explicit narrowing may no longer be deliverable; no automatic reassignment or release migration is performed.

Each dispatch records the bundle's version and the fingerprint of every skill of the session it went to: the `bundle` and `skills` of its `dispatch.changed` entries in the journal, and of the `session.started` entry. Its `unqualified` marks each skill that is not the bundle's as `user` or `repository`.

#### Added and repository skills

`leader_added_skills` and `worker_added_skills` in `[roles.<role>]` add skill directories, each holding a `SKILL.md`, to the role's leader's or workers' list (08 rules 23-24). An added skill is named by its directory's name, and one whose `SKILL.md` gives it another `name` is refused, so the agent does not start; one with the name of a skill on the list replaces it for that role, and any other joins the list. Added skills are copied into the session's plugin each time an agent starts, so editing one never changes a running agent: its next start picks the edit up. A leader's index of its workers' skills marks added ones as the user's and unqualified, and gives their purpose and when they apply from their own descriptions.

`repository_skills` in `[repositories.<name>]` switches the repository's own skills, the directories in its `.claude/skills` with a `SKILL.md`, on for the roles it names (rule 25). Only workers carrying an assignment in that repository's jobs are given them, copied from the assignment's workspace at each start, after the list the assignment narrowed to; a repository skill named like one on the role's list is left out, and one whose `SKILL.md` gives it a `name` other than its directory's is refused, so the agent does not start. They are marked as the repository's and unqualified. An added or repository skill holding a symbolic link is refused, so the agent does not start, and a repository whose `.claude` or `.claude/skills` is a symbolic link has no repository skills. Nothing else reaches an agent: its skills are the bundle's, added skills and switched-on repository skills (rule 26).

### The conversation

A bare `asmai`, or `asmai chat`, is your conversation with Coordination. If the factory is stopped, it starts it first and says so, then attaches your terminal to `leader@coordination` the way `asmai attach` does, except that what you type reaches Coordination exactly as typed, Esc included, even in the middle of its turn. The status line reads `leader@coordination · conversation · Ctrl-] leaves`.

Every message you submit there is journaled word for word as a `message.witnessed` entry: your words, the agent and session generation you typed them into, your terminal (such as `/dev/pts/3`) and when. The daemon relays your keys, so it knows which Enter keys you typed, and journals a message only when Claude Code confirms a prompt submission after one of them; the entry cites that `observation` by its journal ID. Text you typed but never submitted is never a witnessed message, and neither is a prompt submission no key of yours caused.

Coordination opens a tested-PR job with `asmai job open --message latest --repository <name> --reading <text> --mandate tested-pr --criterion <text>`, repeating `--criterion` for each acceptance criterion. `latest` resolves to the newest witnessed message submitted to Coordination's leader and records its journal ID; a specific ID can also be cited. An observation or nudge is refused, as is a repository you have not registered; Coordination tells you to run `asmai repo add <path-or-url>` in that case. The numbered job records your words beside Coordination's reading, its mandate, acceptance criteria, repository, role and state. `asmai jobs` and `asmai job <number>` show it to you; agents load `asmai brief <number>`, generated from the store, when they switch jobs.

From your first key until Claude Code confirms your message submitted, you own Coordination's input; otherwise automation does, so delivery never waits on your being there. Ctrl-] leaves the conversation: it is not an intervention, so leaving pauses nothing and returns Coordination's input to automation at once. `conversation.entered` and `conversation.left` entries record each visit. One terminal at a time holds the conversation; `asmai chat` in another is refused until you leave the first.

Everything the factory keeps on the host is in the state directory, `~/.local/state/asmai`, readable only by the user:

- `store.db`, the store: an SQLite database, built into `asmai`, that only the daemon opens. It holds the factory's current state and the journal of everything that happened, and writes each change in the same transaction as its journal entry. The journal is append-only and never trimmed. Inspect it with `asmai export`, never by editing it.
- `daemon.sock`, the daemon's socket.
- `daemon.log`, the daemon's log, which rotates through 5 files of 20 MB (`daemon.log`, then `daemon.log.1` to `daemon.log.4`, the oldest).
- `daemon.lock`, held by the running daemon.
- `providers/`, AsmAI's own copies of the provider CLIs, one directory per provider and version, such as `providers/claude-code/2.1.292/claude`.
- `bin/asmai`, the daemon's copy of `asmai`, which each start replaces: agent sessions run it, first on their `PATH`, and their hooks name it.
- `githooks/`, the git hooks that add the commit trailers to a worker's commits, rewritten at each start.
- `agents/`, each agent's working directory, by its address, such as `agents/leader@coordination`.
- `repositories/`, AsmAI's own clone of each registered repository, in a directory named for it.
- `workspaces/`, each assignment's workspace and temporary directory, as `workspaces/job-<n>/assignment-<id>/repo` and `.../tmp` (see [Writing assignments](#writing-assignments) and [Validation](#validation)).
- `views/`, the leaders' read-only view of each repository job, as `views/job-<n>`.

No journal entry or log line records environment variables.

### Writing assignments

Engineering's leader does not write code itself: it gives a writing assignment to a worker with `asmai assign --job <number> --outcome <text> --criterion <text>`, repeating `--criterion` for each acceptance criterion. Only Engineering's leader may. The assignment is recorded with its owning leader, its worker, its outcome and its acceptance criteria, and moves from active to submitted when its worker submits a result.

The daemon, and only the daemon, makes the branches. A repository job's **job branch** is made as the job opens, from the repository's default branch as AsmAI's clone has just fetched it from origin, and is named `asmai/job-<n>-<slug>`, the slug taken from Coordination's reading of the request. The `job.branch` journal entry records the commit it started from. When an assignment is given, the daemon makes its **workspace**: a checkout of AsmAI's clone, never your own checkout, on a new **assignment branch** `asmai/job-<n>/<assignment>` made from the job branch's tip. The checkout shares the clone's configuration, so the worker pushes the branch to the repository's origin. The workspace has a **slot**, the lowest number no live workspace holds, and a temporary directory of its own beside the checkout; the worker starts in the workspace on Engineering's configured worker provider and model with `ASMAI_SLOT` and `TMPDIR` set to them, and is nudged like a leader. Worker numbers start at the lowest free number and are reused once a worker's assignment ends, so the worker is `worker1@engineering` and a durable record names it together with the assignment ID. The job branch moves only when the owning leader accepts a result.

The daemon also keeps one **read-only view** of each repository job at the job branch's tip, in `views/job-<n>`, with its files made read-only. Leaders read the job's code there, `asmai brief <job>` points to it, and leaders never write in it.

The worker writes tests along with the code, runs the repository's checks, takes in the job branch's tip, commits, pushes its assignment branch, and records each effect immediately with `asmai effect <kind> <ref>`, such as a commit or a push. The ledger is evidence, not proof: git is not routed through `asmai`. Then it submits its result:

```sh
asmai result --evidence <text> --test <text>|none --check '<command> -> <outcome>'|none --gap <text>|none --pr-section <text> [--artifact <text>]
```

A result links its artifacts and evidence, names the tests added and the checks run with their outcomes, discloses every gap, and carries the worker's PR section: what changed, with before-and-after evidence. Leaving a list out is refused, so that omission is never taken for none. The daemon adds what it saw: the commit the workspace was at, the job branch's tip and whether the commit has taken it in, and the effects recorded in the dispatch. It refuses a result while the workspace has changes that are not committed. The result goes to the owning leader as a message with a dispatch of its own. A worker that cannot go on runs `asmai blocked --reason <text> [--needs <text>]` instead, which leaves the assignment active. A dispatch ends in one report. A message saying the worker is done is never a result.

Only the owning leader decides a submitted result. The leader accepts it against the assignment's criteria with `asmai accept --assignment <id> --reason <criterion and evidence>`, repeating `--reason` for each criterion; acceptance records the decision and fast-forwards the job branch to the accepted commit, then refreshes the read-only view. The assignment ends and its writing workspace is removed after its work reaches the job branch. If the commit is not a fast-forward of the current job branch tip, acceptance is refused and nothing moves. The leader rejects with `asmai reject --assignment <id> --reason <criterion not met and what is needed>`; the same worker gets a new dispatch and the assignment becomes active again. To stop work, its owning leader runs `asmai cancel --assignment <id> --reason <why>`. The worker must commit and push its assignment branch before stopping; cancellation completes only after the daemon confirms that push and the worker has stopped.

### Validation

When Engineering's leader decides a job branch is finished, it hands validation to Quality with `asmai handoff send --job <number> --to quality ...`; only Engineering's leader may. Two things must hold, and the daemon checks both before the handoff is sent. No writing assignment of the job is still live. And the job branch has **taken in the latest base**: AsmAI's clone fetches origin, and the repository's default branch's tip must be in the branch's history. If the base moved, the handoff is refused with the commit it moved to. Engineering then assigns a worker to merge `origin/<default branch>` into its assignment branch, and accepts that result through the same accept path as any other, which fast-forwards the job branch. The handoff names the job branch's tip as the exact head commit to validate, and starts Quality's leader if it is not running.

Quality's leader accepts the handoff and assigns the validation with `asmai assign --read-only --commit <the head the handoff names> --job <number> --outcome <text> --criterion <text>`; only Quality's leader may, and the daemon refuses any commit that is not the job branch's tip, a second validation of a job while one is running, and a writing assignment from Quality. A validation is a **read-only assignment**: its workspace is a clean checkout of AsmAI's clone fixed at that exact commit, detached, so that it has no branch to push, and the worker, `worker1@quality`, is started in it with a slot and a temporary directory of its own and is given the job's intent: the user's words, Coordination's reading, the mandate and the job's acceptance criteria. Quality's instructions forbid fixing, and the daemon refuses a report from a workspace that has moved off its commit. The workspace is removed when the assignment ends, by acceptance or cancellation.

The worker re-runs the repository's checks, reviews the change against the repository's instructions and against the mandate and acceptance criteria, and submits a validation report with `asmai result`:

```sh
asmai result --evidence <text> --check '<command> -> <outcome>'|none --gap <text>|none --finding '<blocking|advisory|needs-you>: <text>'|none [--resolved <id>] [--unresolved <id>]
```

The report records the exact head commit the workspace was at, the checks re-run and their outcomes, and each finding with its kind and text. A **blocking** finding must be fixed, an **advisory** one is listed in the pull request and needs no fix, and a **needs-you** one challenges the user's stated intent or a recorded decision, so it goes to the user. When the job has earlier blocking findings that are still open, the report says for each, by ID, whether it is resolved at this commit (`--resolved`) or still open (`--unresolved`), and is refused until it does.

The report goes to Quality's leader, which checks it against the assignment's criteria and either rejects it back to the same worker or accepts it with `asmai accept --assignment <id> --reason <text>`. Acceptance records each finding with its ID, clears the earlier blocking findings the report confirms resolved, ends the assignment and delivers the report to Engineering's leader as a `validation` message. Nothing about the job branch changes. A blocking finding is fixed by Engineering's leader as a new writing assignment; after its acceptance, and a new handoff, Quality validates the new head. Only a validation or the user's decision clears a blocking finding. `asmai brief <job>` lists the job's findings and which blocking ones are still open.

### Pushing the job branch

Once Quality passes the job branch's head, Engineering's leader, as the job's **delivery owner**, asks the daemon to push the job branch with `asmai push <job>`. Only the delivery owner may, and only while it works on a dispatch, and only the daemon ever pushes the job branch. The daemon first fetches the branch from origin. If origin's branch has commits AsmAI did not make, it pushes nothing: the refusal is recorded as an **outside change**, with the commits and where they were found (`outside_change.found` in the journal), and the leader is told the commits. A worker merges them in through a writing assignment, the leader accepts its result, Quality validates the new head, and the leader asks for the push again; the outside change records the commit of the push that took it in. Otherwise the daemon pushes with a plain push, never forced, which origin refuses unless it is a fast-forward, and records the push as its own effect, of agent `daemon`, tagged with the leader's dispatch (`job.branch.pushed` in the journal). `asmai brief <job>` lists the job's pushes and outside changes. The repository's instructions never change how the job branch is pushed. [Qualification](docs/qualification-harness.md) case C41 checks the push against the fixture repository on GitHub.

### Opening the pull request

After the push, Engineering's leader opens the job's pull request itself with `gh`, from the job branch, as a draft. If GitHub refuses a draft, it opens normally with "[not ready]" at the start of its title. The leader composes the body from the workers' PR sections, Quality's report and CI, following the repository's PR template where there is one and otherwise the pr skill's template, and adds an AsmAI section: the job and its mandate, the head commit Quality passed, the checks and CI results, the advisory findings and the gaps. It links the originating issue with "Closes #n" only when the mandate is to resolve it, and "Refs #n" otherwise. It then records the pull request with `asmai effect pull-request <url>`, which is how the daemon learns which pull request to follow: the daemon looks it up with `gh pr view`, refuses one that is not open, not in the job's repository or not from the job branch, and records its number and whether it is a draft or "[not ready]" with the effect (`pull_request.recorded` in the journal). If the lookup fails, nothing is recorded. `asmai brief <job>` shows the pull request the daemon follows. No review is posted, and nothing in AsmAI merges. [Qualification](docs/qualification-harness.md) case C42 checks the draft, and the "[not ready]" fallback, on the fixture repository.

### Watching CI and delivering the job

The daemon follows CI itself, through `gh` and with no agent. For each open job with a pushed head and a recorded pull request, it reads the checks on the pull request's head with `gh pr view --json statusCheckRollup` in AsmAI's clone, looking again after a second, then less often, up to every 30 seconds, and records each check's state each time they change (`checks.observed` in the journal). A head with no checks is never green: the daemon keeps waiting. When every check on the head it pushed is green, and that head is the one Quality validated, with no blocking finding open and no assignment live, it marks the pull request ready for review: a draft with `gh pr ready`, and one opened with "[not ready]" by taking that out of its title with `gh pr edit`. It then records the **delivery**, with the pull request, the head commit and the time (`job.delivered`), ends the job (`job.ended`), and tells Coordination's leader in a message of kind `delivery`, which reports it to the user with the link, in a line tagged with the job's number. Everything local to the job is removed: its workspaces, its view and its branches in AsmAI's clone (`job.local.removed`); its branches stay on origin, and nothing about the job is watched afterwards. AsmAI never merges: ready never means merged. `asmai brief <job>` shows each check's state and the delivery. [Qualification](docs/qualification-harness.md) cases C43 and C45 check the watch and marking the pull request ready on the fixture repository.

### Red CI

When the checks on the head the daemon pushed are red, it tells Engineering's leader in a message of kind `checks-red`, naming each failing check on that head, once each time they turn red, and once more when they are red after a judged re-run. If the leader judges the failure unrelated to the change, it may have the failed jobs re-run once for that head by recording its judgment as a delegated decision: `asmai decision record --job <job> --choice rerun-failed --rationale <text> --evidence <text>`. The daemon then re-runs them with `gh run rerun <run> --failed` in AsmAI's clone and records the decision, with the job, the choice, its rationale and evidence (`decision.recorded`), and the **judged re-run** with the head, the runs and the failed checks (`checks.rerun`). A second re-run of the same head is refused, and only red GitHub Actions checks on the pushed head can be re-run. Otherwise, or when the re-run is red again, the leader assigns a fix as a new writing assignment, accepts it, hands the new head to Quality and, once Quality passes it, asks for the push. The daemon then watches the new head and drops its wait on the old one (`ci.wait.replaced`). Whenever the evidence changes, the leader updates the pull request body with `gh pr edit` and records each update with `asmai effect pull-request <url>`. `asmai brief <job>` shows the judged re-runs and the decisions. The judged re-run is one kind of decision (see [Decisions](#decisions)). C43 checks the red path, with one re-run, and a newer push replacing the wait, on the fixture repository.

### Decisions

A leader records a decision that affects later work with `asmai decision record --job <number> --choice <text> --relied-on <the mandate or grant> --rationale <text> --evidence <text> --assumption <text>|none --reopen-when <text>|none`, repeating `--assumption` and `--reopen-when` for each. The daemon takes the accountable leader from the session that runs it, and keeps the **decision record** with the job, the mandate or grant relied on, the choice, its rationale and evidence, its material assumptions, the conditions that would reopen it, and its source (`decision.recorded`). A record without its choice, rationale, evidence or what it relied on is refused, and so is one from a worker: a worker's decision goes to its owning leader. The source is `delegated` unless the decision is the user's own, which is recorded with `--source human --cites <witnessed message>` and is refused unless that witnessed message belongs to the job: the job's own request, or a later witnessed message to the same agent. A routine edit, or a choice that the repository's conventions or the mandate already settle, needs no record, and nothing asks for one.

The owning leader passes the records that matter on: `--record <id>` on `asmai assign` and `asmai handoff send`, repeated for each, puts them in the assignment's or the handoff's own record, and `asmai inbox` shows them in full to the worker or the receiving leader. Only the job's own records can be passed. Each job's brief lists all of its decisions with every field, and marks the handoffs and assignments they were passed with. The records are part of the store, so they survive `asmai stop` and `asmai start`: a restored leader loads them with the brief, and a resumed worker reads them again in its assignment. The judged re-run is one kind of decision, with the choice `rerun-failed`, whose record also makes the daemon re-run the failed jobs once per head. The user's answer to a choice in the conversation is one kind of human decision (see [Decision requests](#decision-requests)); their answers in Lavish arrive in a later ticket of M3, and grants are the next section's.

### Decision requests

Any agent asks for a choice that is not its own with `asmai decision request`. A worker's request goes to its owning leader and never to you: the leader answers it from the records, or escalates it with a request of its own, and a leader's request reaches you through Coordination. A single choice is `--title <text>` with an `--option <text>` for each choice (and `--recommend <option>`); several questions are given as `--question '<json>'`, each with an `id`, `title`, `body`, `options` and `recommendation`, and `--content <text>` puts the agent's own content above them. A leader's request names its job with `--job` and the assignments of its own whose work waits with `--blocks <assignment>`.

Every request is versioned. `--request <id>` issues a new version, which replaces the pending one and shows it as replaced; an answer applies only to the version it names, so `asmai decision answer --request <id> --version <n> --answer <text>`, the owning leader answering a worker's request, is refused for a version that was replaced. A request is pending, answered, replaced or withdrawn. Each version has one answer surface, fixed when it is made: the conversation for a single choice (`--kind choice` or `provider`), Lavish for everything else (`review`, `grilling`, `wayfinder`, and requests with several questions).

While a request is pending, work that depends on the choice waits and independent work goes on: a worker's own assignment cannot submit a result, nor can the leader accept one, until the request is answered, and a leader's request holds the assignments it names. Silence or time is never approval. A paused job's pending requests stay answerable, and cancelling a job withdraws them (`JobDecisionsWithdrawn`; the pause and cancel commands themselves arrive with M5). `asmai decisions` lists what waits for you, with each request's answer surface; it is not another way to answer. A choice between distinct viable approaches is yours to make, and the leaders' instructions say when to ask: whenever more than one distinct viable approach remains after the agreed constraints, the repository's conventions and any grant, even when both are reversible and the leader recommends one. Approaches are distinct when they differ in behavior, dependencies, interfaces, cost, maintenance or operational consequences; equivalent ways of expressing the same thing, and routine choices that conventions, the job's decisions or a grant already settle, need no question, and neither does ordinary authorized work along a settled route.

A single-choice escalation is answered in the conversation, and Coordination presents it there once. It shows you the question, the options and the leader's recommendation and says you answer in your next message, then runs `asmai decision present --request <id> --version <n>`, which journals that the version was shown (`decision.presented`) and fixes the entry you must answer after. Your next message is the answer. Coordination records it with `asmai decision record --request <id> --version <n> --cites latest --choice <text> --reading <text>` (`latest`, or a witnessed message's journal ID). That is a human decision citing your witnessed message, which the daemon reads the words from, with Coordination's reading of them beside them; the version is answered by you (`decision.answered`), and the owning leader that asked receives a message with your words, the reading and the decision record, which it passes on with `--record <id>`. No agent supplies your answer: `asmai decision answer` refuses a request that goes to you, and only Coordination presents a version or records an answer to it.

The daemon refuses a record that cites an entry that is not a witnessed message, such as a nudge, or a message from before the version was shown, which you typed against an older version, and one that names a version a newer one replaced. It journals the refusal (`decision.refused`), clears the presentation, and shows the current version in the refusal so that Coordination presents it to you again and takes your next message. Until it is presented again no answer is taken. A version already presented is not presented a second time, and a new version, issued on material new evidence, replaces the old one and is presented in its turn. A message to another agent's terminal is not your answer in the conversation, and answering in Lavish arrives in a later ticket of M3. The decision record, with the witnessed message it cites and Coordination's reading, is in the job's brief and in the owning leader's inbox, and `asmai brief <job>` lists the job's pending requests.

### Grants

A grant is your authorization of an exact decision or action, given in your own words, in the conversation or in an answer to a decision request, at a scope: one job, one registered repository or the whole factory, with the conditions it holds under. The default mandate never covers deployment, spending money or destructive changes outside the job, and each needs a grant. Spending is zero unless a grant names the amount and the scope, and no grant can authorize a merge: AsmAI never merges, so a grant of `merge` is refused whoever records it.

A leader records a grant with `asmai decision record --grant --scope job|repository|factory [--job <number>|--repository <name>] --action spend|deploy|destructive|decision --approved <text> --condition <text>|none [--amount <n> --currency <code>]`, citing your words: Coordination's leader one you gave in the conversation, with `--cites <witnessed message>` (or `latest`), and the leader that asked one you gave in an answer, with `--answer <the answer's decision record>`. The daemon keeps the **grant** with its scope, the exact action approved, its conditions, who recorded it and your words word for word, and journals it (`grant.recorded`). It refuses a grant without a valid citation: a nudge, a message you typed to another agent, an answer to somebody else's request, a message from before the job's own request (for a grant at a job's scope) or nothing at all. Spending needs the amount, in the currency's units to two decimals, and its currency.

A grant is reused, never asked for again, while its scope and conditions hold: it is listed in every job's brief that its scope covers, and every assignment and handoff carries the grants in force for its job when it is fetched. It lives in the store, so a stop and a start, a handoff or a resumed session alone change nothing. A job's own approval stays with that job: only a grant at a repository's scope covers that repository's other jobs, and only one at the factory's scope covers every job. A changed scope, or a condition that no longer holds, needs a new decision of yours: a leader who finds that a condition no longer holds runs `asmai grant invalidate <id> --because <the condition>`, and the grant authorizes nothing after that.

Before each consequential action it affects, an agent checks the grants again with `asmai authorize --action spend|deploy|destructive --what <the action>` (`--amount <n> --currency <code>` for spending, `--job <number>` for a leader). The daemon authorizes it only when an active grant of that action covers the job, whose conditions have not been reported invalid and, for spending, whose amount the earlier authorizations have not used up, records the authorization (`action.authorized`) and refuses everything else, naming each grant it considered and why it does not cover the action. An agent records the effect of a `spend`, a `deploy` or a `destructive` change with `asmai effect` only for an action that was authorized, once for each authorization and only while its grant is still in force: a grant revoked after the check covers nothing. A grant given in an answer is of the job the request was about (or of that job's repository, or the factory, when you said so).

`asmai grants` lists the grants with their state, what each has spent and your words beside them; it only lists. `asmai grant revoke <id>` revokes one: every later action it covers is refused, and the owning leader of each assignment in flight in its scope is told, in a message of kind `grant.ended`, to stop or revise it and to ask you for a fresh decision where one is needed. What the grant already authorized is reported as it actually stands, with the authorizations it gave and the amounts, and revocation never claims to undo any of it (`grant.revoked`). Agents never revoke a grant; they print the command for you to run.

### Continuing after a stop

`asmai stop` ends every agent session and persists the factory's state: the job, its handoffs, its assignments, the inbox messages and their dispatches, and the journal. Nothing queued or open is lost. Every start is a recovery, and after a clean stop it does this, before it restores any leader:

- **Workers.** A worker whose dispatch stopped at a boundary, with its assignment still active or being cancelled, is run again in its workspace on the same provider, resuming the provider's own session where it can: the daemon records the identifier the session's hooks report, and starts Claude Code with `--resume`. The assignment continues in a **new dispatch**, a message of kind `resumption` that names the dispatch it resumes; a resumption is always a new dispatch, never the old one reopened, and its result is tied to it. A cancellation that was not complete is continued the same way: the worker pushes its assignment branch and stops, and the assignment ends then. A worker that had reported it was blocked waits for its owning leader's decision and is not run again.
- **Assignments that cannot continue.** A worker whose turn was cut off by the stop, whose provider reported no session to resume, whose transcript is gone, or whose resumed session ended before it came up, leaves its assignment **needing reconciliation**. The dispatch whose outcome is unknown becomes `unknown`, the owning leader is told in a message of kind `reconciliation`, and the assignment is held with its worker's number and workspace; nothing is retried. Recording a reconciliation arrives in a later milestone.
- **Leaders.** Coordination always runs, and so does each leader whose role has open work: a handoff open to it, an assignment it owns that has not ended, or a message waiting for it. Each gets a new generation, and one message of kind `restoration`, which names each job it has open work in, for it to load `asmai brief <job>` and fetch `asmai inbox`. Coordination has open work in every open job. A leader is never resumed in its native session: the brief holds the job.
- **Evidence from before the restart.** What the sessions before it reported is in the journal, tied to the generation and the dispatch it came from, and never changes a dispatch of the new generation: a dispatch moves only on evidence of its own generation, a result and every effect stay tied to the dispatch they came from, and a call with the credential of a session from before the restart is refused.

After an unclean stop, which is reconciled in full in a later milestone, the leaders are restored in the same way and no worker is run again.

## Pinned providers

Agents never run your own Claude Code. [`pins.json`](pins.json), the pins file, names the Claude Code version AsmAI runs, Claude Code's official release channel, and the size and SHA-256 of the download for each certified platform; `asmai` embeds it. It also names the Lavish build (below). Codex joins it in a later milestone.

`asmai init` installs the pinned Claude Code as `asmai providers install` does; with the factory stopped, the daemon records the install when it next starts, finding the pinned copy at its path. With the factory running, `asmai providers install` shows what it will fetch, from where, how it checks it and where it keeps it, and asks before it fetches anything. Once you confirm, it downloads the pinned Claude Code from `https://downloads.claude.ai/claude-code-releases`, refuses a download whose size or SHA-256 differs from the pins file, and keeps it in `providers/` in the state directory. The store records the install, with a `provider.installed` journal entry, and `asmai providers list` shows it. Installing a pin that is already installed does nothing.

Only the pinned version runs. Before any agent starts, the daemon asks the copy at its path for its version and sign-in method. It refuses a version that is not the pin, naming both versions and `asmai providers install`, which puts the pinned copy back; it also refuses a signed-out, API-key or unknown sign-in method and names the CLI's `auth login` command. A copy that updated itself under a running agent does not stop that agent, but the agent is held at its next restart: the daemon does not start it on a version outside the qualification record, and `asmai status` names the check, until the pinned copy is back.

AsmAI never redistributes Claude Code, and never runs, changes or replaces your own copy or touches `~/.claude`.

### Lavish

Lavish, the review pages where decisions are answered, is the one provider AsmAI builds itself, so the host needs no Node ([ADR 0010](docs/adr/0010-lavish-is-a-deno-compiled-executable-built-per-pin.md)). The pins file's `lavish` entry names the lavish-axi release and the Deno version it is compiled with, where Lavish builds are published (releases of talvor/asmai), and, once a build is published, the size and SHA-256 of the executable for each certified platform. The [Lavish build workflow](.github/workflows/lavish-build.yml) compiles the pinned lavish-axi for every certified platform when the pins file moves lavish-axi or Deno, and publishes the executables, their notices, checksums and attestations as a release with its own tag (`lavish-v<lavish-axi>-deno<deno>`) that is never marked latest. Every asmai release that keeps the pin reuses that build. Once a build is published, the workflow proposes a pull request that records the digests in `pins.json`; see [`CONTRIBUTING.md`](CONTRIBUTING.md#the-lavish-build).

`asmai providers install` installs the pinned Lavish build beside the pinned Claude Code, after the one confirmation: it downloads the executable for this platform from the build's release and refuses a download whose size or SHA-256 differs from the pins file. It never installs, runs or changes your own Lavish or `~/.lavish-axi`. `asmai providers list` marks each install `pinned`, `superseded`, `missing` or `mismatch`; the daemon runs only a Lavish that is the pinned download, and `asmai notices` prints only AsmAI's own license and the third-party notices of what is compiled into `asmai`; the Lavish build's notices travel with the Lavish release instead.

The daemon runs the factory's Lavish server itself, in the foreground, so that review pages outlive any agent. It has its own state directory, `lavish/` in the state directory, and its own port, 14387, never Lavish's defaults, which your personal Lavish uses. It binds `127.0.0.1` only, so it never also listens on a Tailscale address, and has telemetry and the browser launch off. The daemon starts it with the factory, restarts it whenever it exits, and checks it every 30 seconds, restarting it when it does not answer, listens on another address, or serves another state directory. Review pages are kept in the state directory, so they survive a restart of the server and of the daemon. No agent runs Lavish and no Lavish skill is shipped.

`asmai lavish` lists the review links waiting for you and the command that forwards the server's port over SSH, for when the factory runs on another machine:

```sh
asmai lavish
```

## Building

AsmAI needs Go (the version in [`go.mod`](go.mod)) and no C compiler. Build `asmai` for Linux x86_64 and macOS on Apple silicon with CGo disabled, and run the development tests:

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -o dist/linux-amd64/asmai ./cmd/asmai
CGO_ENABLED=0 GOOS=darwin GOARCH=arm64 go build -trimpath -o dist/darwin-arm64/asmai ./cmd/asmai
CGO_ENABLED=0 go test ./...
```

The [`Makefile`](Makefile) wraps these and other everyday tasks: `make dist` runs the two builds above, `make test` the tests, `make notices` regenerates `THIRD_PARTY_NOTICES` (see [`CONTRIBUTING.md`](CONTRIBUTING.md#third-party-notices)), and `make qualify` builds the [qualification harness](docs/qualification-harness.md) into `bin/qualify` (development builds only), and `make build`, `fmt`, `vet`, `tidy` and `clean` do what they say. Run `make` or `make help` to list them.

[CI](.github/workflows/ci.yml) does the same on every pull request, on a hosted Linux runner and a hosted macOS runner. It also checks every Go module compiled into `asmai` against the license allow-list (see [`CONTRIBUTING.md`](CONTRIBUTING.md#the-license-allow-list)), and that the embedded third-party notices match what generation produces (see [`CONTRIBUTING.md`](CONTRIBUTING.md#third-party-notices)):

```sh
go run ./internal/cmd/check-licenses
go run ./internal/cmd/gen-notices -check
```

## Repository layout

- [`cmd/asmai/`](cmd/asmai/): the `asmai` executable.
- [`qualification/`](qualification/): the qualification harness, its own executable that runs the qualification cases against the real pinned providers on a qualification host. It is built only into development builds, never into `asmai`, and never runs in hosted CI.
- [`pins.json`](pins.json): the pins file, embedded in `asmai`.
- [`internal/`](internal/): packages used only by AsmAI.
- [`internal/fakeprovider/`](internal/fakeprovider/): the scripted fake provider CLI the development tests drive, its script format, and the recorder that records a real Claude Code session as a script. Neither is built into `asmai`, and the fake never counts toward qualification.

- [`docs/adr/`](docs/adr/): architecture decision records. New ADRs are numbered from 0011.
