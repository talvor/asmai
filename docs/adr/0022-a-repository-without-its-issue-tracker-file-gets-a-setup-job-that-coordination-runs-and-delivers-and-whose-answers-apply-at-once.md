# A repository without its issue tracker file gets a setup job that Coordination runs and delivers, and whose answers apply at once

The specification says that registering a repository without `docs/agents/issue-tracker.md` makes Coordination open a setup job straight away, that a Coordination worker runs the setup skill and its questions reach the user as decision requests, that the files go on the job's branch and pull request which Coordination's leader delivers like a notes-only job, that the answers are recorded for the repository so a job that starts before the pull request merges receives them as repository instructions, and that whether the repository has CI is the user's to declare in the configuration, which Coordination gives them as a change to make (05 rule 4, 08 rules 27 to 31). A job opens from the user's witnessed message, a role other than Engineering, Planning and Research never gave work to a worker or delivered a branch, and the daemon's delivery assumed a leader that works on a dispatch, so each needed a decision.

**New rule.** `asmai repo add` makes the daemon open the repository's setup job in the same store transaction as the registration, when the clone has no regular file `docs/agents/issue-tracker.md`; that file alone decides, and with it nothing is opened. The job has a new `setup` mandate, which only the daemon opens (`asmai job open` refuses it), and its request is the registration the user ran: it cites that journal entry, not a witnessed message, and its words are the command. The daemon makes its job branch and tells Coordination's leader with a message of kind `setup`.

- **Coordination is the owning and delivery leader.** `asmai assign`, `accept`, `reject`, `cancel`, `push` and `effect pull-request` take leader@coordination, but only for a setup job, and a setup job's writing work is only Coordination's (`onlyRole`), as a notes job's is only its role's. A setup job is a notes job for delivery (`Job.Notes()`): no Quality validation, a draft pull request with a short body, marked ready on green CI, or straight away where the repository declares `no_ci`. It is handed to no other role. Its workers, `worker<n>@coordination`, run unattended in `dontAsk` mode: only Coordination's leader's terminal takes the user's keys, which the daemon now tests by address and not by role.
- **Every setup question goes to Lavish.** A worker's questions reach its owning leader, Coordination's, which carries them to the user as its own request (`--carries`), as Planning does for grilling. The daemon forces the answer surface of a setup job's request to the user to Lavish, even a single choice, so that every answer arrives as the user's own words, by question.
- **The answers are recorded at once.** When the user sends a setup page, the same transaction that collects it records each answer for the job's repository (`setup_answers`, `setup.answered`), citing the Lavish answer, before the version is complete. The latest answer to a question stands, the review of the drafts is no answer, and removing the repository clears its answers. `asmai brief <job>` lists them for every job in the repository, and a worker that starts in a workspace without `docs/agents/issue-tracker.md` is given them after the repository's instruction files and the user's notes. The merged files carry them afterwards, so the check is the workspace's own file and the daemon follows no pull request state for it.
- **CI is the user's change to make.** The worker always asks the question with the id `ci`, with the options `yes` and `no`, which the setup skill does not ask. The daemon reads the user's choice and, in a message to Coordination as soon as they answer, in the brief and in the delivery message, gives the change when the repository has no CI and the applied configuration does not declare it: set `no_ci = true` in `[repositories.<name>]` and run `asmai config apply`. No agent edits the configuration.

## Considered Options

- **The daemon opens the job from the registration** (chosen): the job exists even when Coordination is not running or the leader fails, and cites what happened.
- **Coordination opens it with `asmai job open` when nudged:** the same shape as every other job, but a job needs a witnessed message of the user's and the registration is a command, so the daemon would have to forge a citation or the job would wait on the leader.
- **A setup role with its own leader:** no new coupling to Coordination, but a sixth role for one job, and the specification gives the setup to Coordination's worker and its leader.
- **Ask in the conversation when a question is a single choice:** the usual surface for a choice, but its answer is a witnessed message that Coordination reads, and the setup's answers are recorded from the user's own words by question.
- **Record the answers from Coordination's decision records:** the leader supplies the words, which an agent never does for the user.

## Consequences

- Registering a repository without its issue tracker file opens a job, so a test fixture repository carries the file unless it tests the setup.
- A repository's no-CI declaration has one more effect: a setup pull request is delivered straight away under it, and waits for checks that never come without it.
- The answers stop being given to a workspace once it has the repository's setup, so a worker that starts after the setup pull request merges is given none.
- A setup pull request that is closed unmerged is not followed: no job or message handles it, and the user registers the repository again or asks for the setup in a new job.
