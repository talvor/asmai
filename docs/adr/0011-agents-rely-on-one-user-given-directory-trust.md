# Agents rely on the user's own trust of the agents and workspaces directories and each repository's clone

Claude Code asks whether to trust a folder the first time a session starts there, before any hook runs. Only Coordination's terminal takes the user's keys, so every other leader would wait at that question with no one able to answer it. So would every worker, since each assignment gets a new workspace. On Claude Code 2.1.292, trusting a folder also trusts every plain directory below it, but not a git repository below it: Claude Code records and looks for a repository's trust at its main repository's root, and trusting that root covers every existing and future worktree of it. A worker's workspace is a git worktree of AsmAI's clone, `repositories/<name>`, so only the clone's own trust covers it. So `asmai setup` opens the pinned Claude Code once in `agents/`, once in `workspaces/` and once in each registered repository's clone in the state directory, and the user answers "Yes, I trust this folder" themselves. `asmai repo add` says when the new clone is untrusted and to run `asmai setup`, which then asks only about the new clone. Claude Code records that trust; AsmAI writes nothing to `~/.claude.json`. Before starting any agent, and in `asmai start`'s checks, the daemon reads the provider's record and refuses to start the agent if the folder Claude Code looks for its trust at is not trusted, naming `asmai setup`: for a plain folder, the folder or one above it; for a worktree, the main repository it is checked out from. `asmai start`'s checks cover `agents/`, `workspaces/` and every registered clone. The `repositories/` folder itself and `views/` are left untrusted, because no agent starts there, and trusting `repositories/` would not cover the clones in it.

## Considered Options

- **The user trusts the two directories once, at setup, and each repository's clone once, at the setup after it is registered** (chosen).
- **The daemon writes a trust entry for each directory into `~/.claude.json`**: no screen to recognise, but it writes the user's provider state through an undocumented field, races Claude Code's own rewrites of that file, and leaves one entry behind per assignment.
- **The daemon answers the trust screen itself**, as the qualification harness did on one host: no file written, but it reads the screen of each version, and the trust would be the factory's keypress rather than the user's.
- **Trust the whole state directory**: one answer instead of two, but it would also trust the views, where no agent starts, and on 2.1.292 it would still not cover the clones' worktrees, which are git repositories below it.
- **Start workers in a plain folder Claude Code trusts by inheritance**: no answer per repository, but a worker must work in a checkout of the repository, which is itself a git worktree.
- **Fixed workspace paths per slot, so each is trusted once**: a large layout change made only to work around the prompt.

## Consequences

- Claude Code does not document that trust covers subdirectories, and its changelog shows this behaviour has changed before. Nor does it document that a repository's trust is kept at its main repository's root: a probe of 2.1.292 found a repository and its worktrees below a trusted folder asked, and a worktree's answer recorded under the main repository's root. A qualification case, C48, proves both for each pin: with `agents/` trusted, a new agent directory starts with no trust question, and with a registered clone trusted, a new worker's worktree of it, made as the daemon makes one, starts with no trust question either. The harness trusts its own state directory through the same setup step and no longer answers trust screens itself.
- A trusted workspace holds repository content. That is acceptable because agents start with `--setting-sources user` and `--strict-mcp-config`, so a repository's `.claude` settings, hooks and MCP servers never load anyway.
- Moving the state directory, a user removing the trust, or registering a repository makes agents refuse to start until setup is run again.
- Other native prompts that come up mid-work, such as network hosts and commands the write guard does not allow, are not covered here. They wait for interventions.
